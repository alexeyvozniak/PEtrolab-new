# PetroLab2 UI/UX workflow

Этот документ задаёт обязательный процесс для любой задачи, затрагивающей пользовательский интерфейс или пользовательский сценарий.

## 1. Сначала сценарий, потом экран

Перед изменением UI агент обязан сформулировать:

- кто пользователь в этом сценарии;
- что он пытается сделать;
- какое состояние системы считается успехом;
- какие промежуточные состояния обязательны;
- какие ошибки и неоднозначности нужно показать пользователю;
- какие действия опасны для данных и требуют явного подтверждения.

Нельзя начинать с перестановки кнопок или компонентов без привязки к сценарию.

## 2. Обязательные состояния экрана

Для каждого изменяемого экрана проверять как минимум:

- пустое состояние;
- нормальное заполненное состояние;
- состояние загрузки;
- состояние ошибки;
- состояние частично валидных данных;
- состояние с большим количеством строк/точек;
- состояние с длинными названиями образцов, минералов, методов и файлов;
- состояние после выделения/фильтрации;
- состояние после отмены или возврата к исходным данным.

## 3. Визуальная иерархия

На одном экране должно быть понятно без чтения документации:

1. где пользователь находится;
2. что является главным объектом работы;
3. какое действие основное;
4. какие действия вторичные;
5. что изменилось после последнего действия;
6. есть ли ошибка, предупреждение или несохранённые изменения.

Primary action на одном локальном участке интерфейса должна быть одна. Вторичные действия не должны визуально конкурировать с ней.

## 4. Плотность интерфейса

PetroLab — профессиональный scientific desktop tool, поэтому интерфейс может быть плотнее consumer-приложений, но плотность должна быть управляемой.

- Не заменять полезные данные декоративными пустотами.
- Не делать мелкий текст ради компактности.
- Не прятать постоянно нужные действия в меню только ради минимализма.
- Для больших таблиц использовать фиксированные заголовки, логическую группировку колонок и быстрые фильтры.
- Выделенные строки и точки должны быть легко различимы, но выделение не должно менять данные.

## 5. Научные данные и доверие

UI обязан визуально различать:

- исходные измеренные данные;
- рассчитанные данные;
- интерпретированные/назначенные пользователем значения;
- предупреждения QC;
- исключённые из отображения точки;
- исключённые из расчёта данные.

Нельзя создавать визуальное впечатление, что скрытая точка удалена или что предупреждение означает автоматическое исправление.

## 6. Основные сценарии, которые нельзя ломать

### Новые анализы

Добавить файл → проверить листы → назначить Sample/Mineral/Point/Generation → preview/QC → сохранить → открыть график.

### Работа с графиком

Выбрать тип графика → назначить оси/элементы → построить → выделить точки → увидеть те же точки в таблице → скрыть/вернуть → экспортировать.

### Изображения и точки

Открыть изображение → масштабировать → отметить область/точку → связать с анализом → вернуться к анализу без потери контекста.

### Пересчёт формулы

Выбрать анализы → выбрать модель → увидеть применимость/предупреждения → выполнить расчёт → сохранить результат отдельно от исходного анализа.

## 7. Interaction rules

- Кнопка не должна менять смысл между экранами.
- Иконка без подписи допустима только для общеизвестного действия и при наличии tooltip.
- Опасные действия не должны стоять вплотную к частым безопасным действиям.
- Массовое действие всегда должно явно показывать количество затрагиваемых объектов.
- После действия пользователь должен понимать, что произошло, без необходимости искать изменение по экрану.
- Escape закрывает временные оверлеи/диалоги, если это не приводит к потере введённых данных.
- Enter не должен случайно подтверждать разрушительное действие.
- Keyboard focus должен быть видимым.

## 8. Цвет и стиль

- Основная тема PetroLab — сдержанная зелёная, не синяя.
- Цвет не является единственным носителем смысла.
- Цвета графиков и цвета UI не должны смешиваться семантически.
- Красный используется для ошибки/опасности, а не просто для акцента.
- Жёлтый/оранжевый — для предупреждений, а не для обычного выбранного состояния.
- Контраст текста и интерактивных элементов должен оставаться читаемым при длительной работе.

## 9. Визуальная QA

UI-задача не считается завершённой только потому, что тесты проходят.

Перед завершением нужно:

1. открыть изменённый экран в реальном приложении;
2. пройти основной сценарий мышью;
3. проверить минимум один ошибочный сценарий;
4. проверить экран на узком и широком окне;
5. проверить переполнение длинными значениями;
6. сравнить со связанным эталоном/макетом, если он существует;
7. приложить скриншоты ключевых состояний;
8. убедиться, что изменения не ухудшили соседний сценарий.

## 10. Принцип изменений

Если проблема локальная, исправлять локально. Не проводить редизайн всего приложения по ходу исправления одной кнопки, таблицы или формы.

Если существующий паттерн плох и повторяется в нескольких местах, сначала зафиксировать новый паттерн в спецификации/ADR или design-system документе, затем применять последовательно.

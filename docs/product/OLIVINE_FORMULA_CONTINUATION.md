# Продолжение после первого пересчёта оливина

Ветка `codex/olivine-formula-2026-09-11` основана на PR #20
(`eddb731029910f1a4e5071b687009b37630ca465`). PR #19 с изображениями — отдельная
ветка; не считать её включённой. Перед продолжением проверить актуальные heads
и CI: параллельные PR могли развиться. Не переписывать чужие правки и миграции.

## Что теперь реализовано

- Python: оливин на 4 O, APFU, бинарные Fo–Fa, два явных режима железа.
- Каталог метода с версией, источниками, допущениями и fingerprint реализации.
- Предпросмотр, сохранение и история через существующий NDJSON-сервис.
- Миграция 13: отдельные неизменяемые Calculation Run/Derived Value; сохранение
  одной транзакцией, повторный запрос без дубля, stale-проверка входов и метода.
- UI одного анализа: раскрыть «Формула · оливин, 4 O», выбрать Fe, рассчитать,
  проверить исходные wt.% отдельно от APFU, сохранить, открыть историю.
- Отсутствующие/censored обязательные или присутствующие дополнительные оксиды
  не заменяются нулями. Раздельное железо проверяет также исходную форму колонки,
  а не только её каноническое имя. Никакой неявной конверсии Fe₂O₃ → FeO.

Метод намеренно имеет статус `draft`: математические и интеграционные тесты
не заменяют независимую внешнюю проверку на природных составах.

## Ближайший следующий PR — научная приёмка и удобство оливина

1. Проверить Windows CI **этой ветки**. В родительском PR #20 он упал в UI-тестах
   ожидания/закрытия Python-процесса. Исправление тестового запуска включено здесь,
   но успешный Linux-прогон не доказывает успешную установленную Windows-сборку.
   При падении прочитать первый ошибочный шаг/лог; не снимать тесты и не объявлять
   готовой сборку, у которой инсталлятор не создан и не запущен.
2. Найти независимые опубликованные анализы оливина с известным способом расчёта.
   Проверить права на распространение исходной таблицы; при необходимости включить
   только минимальные тестовые числа и точную ссылку. Не использовать production
   функцию для генерации ожидаемых APFU. Сверить O-базис, атомные массы и режим Fe.
3. Добавить зафиксированные внешние benchmarks (не только идеальную стехиометрию):
   обычный Mg-оливин, Fe-богатый, Mn/Ca/Ni-содержащий, раздельное Fe и изменённый
   состав с диагностикой. Объяснить допуск и влияние округления исходной таблицы.
4. Уточнить научно приемлемую политику F/Cl, P₂O₅ и других дополнительных колонок.
   Сейчас неподдерживаемый компонент в wt.% блокирует расчёт, даже если это ноль.
   Не удалять ограничение молча: добавить метод-специфичное правило, исключения
   в provenance и независимые проверки. Отсутствие колонки — не доказанный ноль.
5. Только после внешней приёмки сменить статус определения метода на `validated`.
   Любое изменение алгоритма требует новой версии, обновления hash и benchmarks.
   Старый Calculation Run должен оставаться неизменным и явно устаревать.
6. Проверить минимальное окно, 200% текст, клавиатуру и screen reader в установленном
   приложении. В длинной правой панели метод и результат доступны прокруткой;
   проверить, не нужен ли согласованный расширенный режим результата.
7. Защитить несохранённый формульный предпросмотр/выбор Fe при смене анализа или
   экрана. Сейчас переключение не меняет БД, но незаписанный локальный ввод теряется.
   Сначала определить поведение (предупреждение или черновик), затем архитектуру.

## Затем — массовый путь и слюды

1. Массовый UI: явные отметки Analysis ID, счётчик и список до запуска; фильтр
   не равен выбору. API сейчас принимает 1–100 уникальных ID и атомарно отказывает
   при любой непригодной строке; не расширять лимит без проверки производительности.
   Решить, как пользователь явно исключает непригодные строки и создаёт новый scope.
2. Добавить формульный предпросмотр на шаг импорта, не смешивая preview_id и
   сохранённый analysis_id. Текущий метод работает только с уже сохранённым проектом.
   Определить контракт фиксации расчёта вместе с импортом; не писать Derived Values
   раньше Measurements и не сохранять ссылки на временные ID.
3. Слюды: прочитать первоисточник Rieder/IMA и конкретный алгоритм нормировки.
   Зафиксировать 22 charges/базис, Fe²⁺/Fe³⁺, F/Cl/OH и вакансии; название метода
   в макете не является готовым алгоритмом. Без измеренного Fe³⁺/H₂O не выдавать
   оценку за измерение. Расчёт APFU и номенклатурное предложение — разные результаты.
4. Сначала независимые эталоны флогопита/аннита, затем Ti/Fe³⁺-богатые и сложные
   природные составы. После этого прямой Python-модуль и запись в реестр, тесты
   сохранения/актуальности, потом UI выбора метода в существующей панели.
5. Не внедрять одновременно Cpx/Opx, амфиболы и все остальные группы. Не менять
   Streamlit v1. Соблюдать дизайн → контракт/архитектура → код → независимые тесты.

## Где продолжать

- `src/petrolab/olivine_formula.py`: чистая математика и валидация состава.
- `src/petrolab/formula_methods.py`: описание и fingerprint метода.
- `src/petrolab/formula_workflow.py`: snapshot, транзакции, повтор, актуальность.

- `tests/test_formula_workflow.py`: эталоны и сохранность данных.
- `desktop/tests/import-workspace.integration.test.jsx`: настоящий React → Python.
- `desktop/tests/formula-browser.html`: **синтетический UI-only** fixture, ответы
  получены из Python; это не тест записи БД через браузер.
- ADR 0019 и QA-отчёт `docs/qa/OLIVINE_FORMULA_2026-09-11.md`.

Проверки: `PYTHONPATH=src:. python -m unittest discover -s tests`,
`PYTHONPATH=src python scripts/validate_contracts.py`; из desktop — `npm run test:ui`,
`npm run test:tauri-contract`, `npm run test:sites`, `npm run build`.
Для real-service UI Python должен импортироваться из текущего checkout.

## Что сделано в этом исправлении

1. Ручная разметка диапазона больше не выдаётся за устаревшее принятие предложения.
   `value` и исходная annotation сохраняются; известное название показывается как
   ручное назначение, неизвестное — как требующее уточнения.
2. После импорта можно выбрать любой контролируемый catalog name/chemical target
   с обязательным основанием. Миграция 12 добавляет `manual_assignment`, сохраняя
   всю историю и порядок решений. Перед обновлением существующей базы создаётся backup.
3. Точные русские названия и распространённые сокращения сопоставляются в Python.
   Полный перевод справочника и поиск по всем синонимам ещё не реализованы.
4. Автоматическое совпадение остаётся в очереди принятия. Только явные решения
   попадают в «Приняты пользователем». Устаревшее решение всегда видно отдельно.
5. Исправлен ограниченный случай отсутствующих/censored F/Cl для полного состава
   оливина. Это не общий пересмотр научного классификатора.
6. Формулы не запускаются. В интерфейсе это указано явно.

## Следующий PR: первый сквозной пересчёт

Цель: пользователь выбирает принятые анализы оливина, видит пригодность входов,
явно выбирает метод и Fe-допущение, получает APFU и Fo–Fa, сохраняет результат,
повторно открывает проект и видит те же значения с provenance.
Оливин — ограниченный первый вертикальный этап; слюды — следующий приоритет
пользователя. Не начинать одновременно все группы минералов.

### 1. Зафиксировать научный метод

- Найти и прочитать первоисточник метода и используемых атомных масс. Не выводить
  исполняемую формулу из картинки эталона или заголовка в спецификации.
- Оформить versioned definition по `schemas/scientific-method-definition.schema.json`:
  ID, версия, citation, область применимости, единицы, базис нормировки, обязательные
  и дополнительные компоненты, Fe-режим, результат, диагностики и допуски.
- Для Fo–Fa явно определить знаменатель и обращение с Mn/Ca/Ni и другими компонентами.
  Не выдавать бинарные доли за полное распределение всех конечных членов.
- Никакой молчаливой нормировки суммы до 100, подстановки нулей, преобразования
  `<DL`, оценки Fe3+ или OH. Неизмеренное, ноль, пропуск и censored — разные состояния.
- Отдельно проверить суммарное и раздельное железо; несовместимые формы нельзя суммировать.

### 2. Реализовать доменный расчёт

- Добавить прямой Python-модуль метода и небольшой реестр исполняемых методов.
  Не помещать формулы в React, Tauri или SQL и не копировать Streamlit state/UI.
- Вход: точные Analysis ID и Measurement ID, состав и единицы, method_id/version,
  параметры и fingerprint значимых входов. Приёмка назначения не означает пригодность
  состава: валидировать входы расчёта заново.
- Выход: APFU, согласованные конечные члены, отдельные предупреждения/ошибки,
  использованные и исключённые компоненты, допущения, fingerprint и версия метода.
- Непригодные строки не теряются: возвратить их ID и конкретную причину, не NaN,
  замаскированный под успешный результат. Ошибка одной строки не должна подменять
  scope всего запуска или молча уменьшать число анализов.

### 3. Хранение и команды

- Использовать контракты `schemas/calculation-run.schema.json` и
  `schemas/derived-value.schema.json`. Сейчас это схемы, а не работающий registry/storage.
- Добавить новую миграцию после актуальной последней; не изменять миграции 1–12.
  Хранить Calculation Run и Derived Values отдельно от Measurements и Interpretations.
- В `src/petrolab/ndjson_service.py` добавить явные команды списка методов,
  предварительной проверки/расчёта и подтверждённого сохранения результата.
  Согласовать имена команд в контракте прежде реализации.
- Перед сохранением повторно проверить fingerprint. Новый состав/параметр/метод
  делает старый результат `stale`; не пересчитывать и не перезаписывать его скрытно.
- Запись запуска и его результатов одной SQLite-транзакцией. Проверить rollback,
  повторный запрос, повторное открытие и старый проект с backup.

### 4. UI/UX

- `desktop/src/MineralsWorkspace.jsx`: после явного принятия минерала — понятное
  действие «Рассчитать формулу», число и точный состав выбранных анализов.
- Выбор метода: базис, версия, Fe-режим и ограничения видны до запуска. Недоступность
  объяснять конкретно, например отсутствует MgO; не заставлять угадывать по серой кнопке.
- Предпросмотр: исходные wt.% и производные APFU различимы, нельзя смешать их в одну
  редактируемую колонку. Показать предупреждения и сохранённые допущения рядом с результатом.
- Проверить переход «Импорт → Минералы → Анализы → формула», сохранность выбора и
  незавершённого ввода, повторное открытие проекта и возврат после ошибки.
- Не оставлять кнопку «рассчитать» с mock-ответом. Пока метод не подключён end to end,
  сохранять честное сообщение о недоступности расчёта.

### 5. Независимая приёмка

- Ожидаемые значения готовить независимо от production-функции: идеальные
  стехиометрические составы и внешняя проверенная таблица расчётов с происхождением.
- Покрыть крайние Fo/Fa, смешанный состав, дополнительный Mn/Ca, пропуск, ноль,
  `<DL`, отрицательное/нечисловое значение, неверную единицу, дублированный компонент,
  разные формы Fe, смену метода и устаревший fingerprint.
- Проверить сохранность исходного файла и Measurement до/после расчёта байтами/значениями.
- Прогнать real Python NDJSON → React сценарий, а затем Windows packaged service
  и установленное приложение. Синтетический browser fixture доказывает только UI.
- В PR приложить скриншоты выбора метода, результата и ошибки, числа пройденных тестов,
  точный commit CI и ссылку на Windows artifact. До результата Windows не писать «прошёл».

## После первого метода

1. Слюды: подтвердить метод/базис, Fe/OH/F/Cl ограничения по первоисточнику;
   отдельные benchmarks для флогопита/аннита и сложных составов. Сохранять расчёт
   и номенклатурное предложение раздельно.
2. Последовательно: Cpx/Opx, амфиболы, гранаты, полевые шпаты, апатит, нефелин,
   перовскит. Названия авторов в master specification — ориентиры, не готовые формулы.
3. Входные требования классификатора по группам: сейчас отсутствие K2O блокирует
   общую проверку. Не удалять complete-core gate без независимых тестов для каждого
   нового набора входов. Отдельно проверить возможных конкурентов при отсутствии летучих.
4. Массовое ручное назначение после импорта: отмеченные Analysis ID, явное число,
   один target/reason, stale-проверка каждой строки, атомарное сохранение и понятная отмена.
   Поиск и фильтры сами не должны становиться выделением.
5. Полный русско-английский справочник с синонимами, отображением вида/группы и
   выбором альтернативного кандидата. Не превращать неоднозначную аббревиатуру в факт.
6. Поиск/счётчики на всём проекте, а не только загруженной странице из 500 анализов;
   сохранение загруженного диапазона и фокуса после решения, просмотр истории в UI.
7. Нативная проверка UI на минимальном размере окна и при 200% масштабе, screen reader,
   клавиатурная навигация списка и сохранность ручного черновика при смене анализа/экрана.

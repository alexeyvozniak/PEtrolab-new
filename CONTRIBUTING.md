# Как вносить изменения

## Перед началом

В issue или PR укажите один наблюдаемый пользовательский результат и связанные идентификаторы `US-*` / `AT-*`. Большая техническая тема без проверяемого поведения сначала разбивается на vertical slices.

## Ветка решения

- Продуктовое изменение: обновить сценарий, acceptance и макет до кода.
- Изменение смысла сущности или границы процесса: добавить/обновить ADR и JSON Schema.
- Исправление реализации без изменения поведения: сохранить контракт и добавить регрессионный тест.
- Миграция данных: описать резервную копию, dry-run, сравнение до/после и путь восстановления.

## Pull request

PR должен содержать:

- что теперь может сделать пользователь;
- какие сущности затронуты;
- какие исходные данные гарантированно не меняются;
- список пройденных AT-сценариев;
- снимки интерфейса для UI-изменения;
- риски, миграцию и откат, если применимо.

Не объединяйте перенос архитектуры, новый экран и научный алгоритм в одном PR.
